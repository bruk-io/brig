## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-0002 item 2's last piece: the embedder asks whether a channel is ready, and brig answers with a verified connect, never path existence, using the mechanism TASK-0001.24 measured. The port keeps the connect and the identity check in infra and the decision in presentation, the way ProcessPort and SupervisorPort already do.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 The public API waits for a channel to be ready up to a deadline and reports ready, not ready, or a typed refusal when the process that called listen() on the answering socket is not in the jail's PID namespace (decision-0005: it proves a jail process called listen(), not that it is the one accepting); the check is the one TASK-0001.24 recorded and decision-0005 decided, reached through a port in presentation/ports.py with a fake for integration tests
- [ ] #2 An e2e battery on real bwrap plants the confused deputy (the reserved path symlinked to a listener outside the jail) and readiness refuses it; its positive control, the jail's own listener at the same path, reads ready; a path that exists with nothing listening reads not ready
- [x] #3 The LikeC4 model shows infra/sockets and the readiness relationship, and likec4 validate and c4lint are clean
- [ ] #4 Every OSError from the peer lookup (SO_PEERPIDFD, the ns/pid readlink, the pidfd re-check), including EINVAL from SO_PEERPIDFD on a reaped peer (measured), is a refusal value: never raised out of the readiness primitive and never a fallback to the bare SO_PEERCRED pid; a test pins it
- [ ] #5 On a kernel without SO_PEERPIDFD (Linux before 6.5), readiness refuses (fails closed) with a typed reason and never falls back to SO_PEERCRED alone; a test pins it

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
### Order of work
1. **Confirm the one identity this whole task hinges on**, before writing any code:
   `Jail.process.pid` (what `create_bwrap_jail` already tracks, decision-0002) is
   `supervisor_argv[0]` ("bwrap") itself as `infra.processes.spawn` exec'd it -- the
   *outer* bwrap process, in the host's own original PID namespace. It is **not** the
   in-jail PID 1. TASK-0001.24's probe measured both, on the same run: `bwrap pid /
   its ns/pid  bwrap=9 ns=pid:[4026532557]` (identical to the probe host's own
   `ns=pid:[4026532557]`) versus `in-jail PID 1 (bwrap child)  host_pid=10
   NSpid='10\t1' ns=pid:[4026532693]` -- a *different* host pid, a *different*
   namespace, found by scanning `bwrap`'s own `/proc` children for one whose own
   `NSpid` ends in `1` (`--as-pid-1` makes the jailed program PID 1 *inside* the new
   namespace; bwrap itself still forks once to get there, on every run measured).
   Readiness has to do that same scan -- it cannot shortcut through `Jail.process.pid`
   directly. This is why step 3 below separates "find and hold the jail's own
   namespace" (once, at jail start) from "verify one connect" (every poll).
2. `infra/sockets.py` gains two new functions (the module AC#3 names, the same one
   TASK-0001.26 put the directory lifecycle in):
   - `jail_pid1_namespace(bwrap_pid: int, deadline: float) -> int | JailPid1NotFound`:
     polls `/proc/<bwrap_pid>`'s children (same scan as TASK-0001.24's `children`/
     `jail_pid1_namespace` helpers) until one's `NSpid` ends in `1`, then
     `os.open`s that child's `/proc/<pid>/ns/pid` and returns the fd -- held open by
     the caller for the jail's whole lifetime (decision-0005 item 1: "holds an fd
     open on that namespace... so the nsfs inode cannot be recycled"). `deadline`
     bounds the poll the same way `_wait_for`-style loops elsewhere in this codebase
     do; `JailPid1NotFound` (a frozen dataclass sentinel, not an exception -- infra
     hands back plain data) if nothing matches before it passes.
   - `channel_ready(path: str, jail_namespace_fd: int) -> ChannelReady | ChannelNotReady | ChannelRefused`:
     one connect attempt, adapted directly from TASK-0001.24's `verified_ready`
     (`backlog/tasks/task-0001.24...md`'s verbatim probe script -- read it as the
     reference algorithm, not something to re-derive) with the two gaps decision-0005
     named fixed:
     - `connect()` raising is `ChannelNotReady` (ENOENT/ECONNREFUSED -- nothing
       listening yet; any other `OSError` here also reads as not-ready, since
       nothing about the peer has been reached at all).
     - `getsockopt(SOL_SOCKET, SO_PEERPIDFD)` itself wrapped in `try`/`except OSError`
       (the probe's own gap, per decision-0005's "the spike's probe let the error
       escape"): `ENOPROTOOPT` (or `AttributeError` if `socket.SO_PEERPIDFD` is
       simply undefined on this interpreter) is `ChannelRefused(KERNEL_UNSUPPORTED)`
       (AC#5); any other `OSError` -- including the measured `EINVAL` from a reaped
       peer (AC#4) -- is `ChannelRefused(PEER_LOOKUP_FAILED)`.
     - The `readlink`/fdinfo re-check step (already wrapped in the probe) keeps the
       same shape: its `OSError` is also `ChannelRefused(PEER_LOOKUP_FAILED)`, and a
       pid mismatch between the two reads is `ChannelRefused(PEER_LOOKUP_FAILED)`
       too (pid reuse: `decision-185`'s own class of bug, closed the way the probe
       closes it).
     - Only once the peer's own `/proc/<pid>/ns/pid` string equals
       `os.readlink(f"/proc/self/fd/{jail_namespace_fd}")` is this `ChannelReady`;
       otherwise `ChannelRefused(PEER_OUTSIDE_JAIL)`.
     No `NS_GET_PARENT` walk (decision-0005 item 2: strict equality only, nested
     namespaces refused, not accepted).
3. `presentation/errors.py`: no new exception type -- decision-0005's three refusal
   reasons become one `ChannelReadinessRefusal` `Enum` (`PEER_OUTSIDE_JAIL`,
   `PEER_LOOKUP_FAILED`, `KERNEL_UNSUPPORTED`) and `ChannelReady`/`ChannelNotReady`/
   `ChannelRefused(reason: ChannelReadinessRefusal)` frozen dataclasses, all three
   **returned**, never raised (AC#1's "reports ready, not ready, or a typed refusal";
   decision-0005 item 5: "never raised out of the readiness primitive"). These live
   wherever `presentation/ports.py`'s other mirrored sentinels do (next to
   `ProcessUnknown`/`SupervisorDoneUnknown`), not in `errors.py`.
4. `presentation/ports.py`: new `ChannelReadinessPort` Protocol, one method --
   `ready(self, path: str, jail_namespace_fd: int) -> ChannelReady | ChannelNotReady | ChannelRefused`
   -- mirroring `infra.sockets.channel_ready` one for one, the same shape
   `ProcessPort`/`SupervisorPort` already mirror their own infra functions. The
   namespace lookup (step 2's `jail_pid1_namespace`) is **not** behind a port: it is
   jail-setup, called once, directly, from `create_bwrap_jail` -- the same way
   `_check_state_dir_reachable` calls `bwrap.covering_ancestor_bind` directly rather
   than through a port, since nothing needs to fake "which pid is bwrap's child" the
   way a test needs to fake "is this channel ready yet."
5. `presentation/api.py`:
   - `create_bwrap_jail`: once `channels is not None and channels.reservations` and
     the supervisor has actually started (so `process.pid` -- the outer bwrap pid --
     is known), calls `infra.sockets.jail_pid1_namespace(process.pid, deadline)`
     inside the existing `try` (the same reasoning as TASK-0001.26's `directories.create`:
     a `JailPid1NotFound` here must not leak the channel directory or the script).
     `Jail` gains `channel_namespace_fd: int | None`, closed by `os.close` in
     `destroy_jail` (swallowing `OSError`, same pattern as every other teardown
     cleanup there) -- `None` when the jail declared no channel, so nothing to close.
     A `JailPid1NotFound` here needs its own typed exception in `errors.py` (unlike
     the three readiness outcomes, this genuinely is a creation failure, not a
     per-poll result) -- name it `ChannelNamespaceNotFound` and translate it at this
     one call site, the driver-exception-boundary rule's own shape.
   - New public function `await_channel_ready(jail, reservation, *, timeout_s=...,
     readiness=_channel_readiness) -> ChannelReady | ChannelNotReady | ChannelRefused`:
     polls `readiness.ready(reservation.bound_path, jail.channel_namespace_fd)` on a
     short interval until `ChannelReady`/`ChannelRefused` (both terminal -- a
     refusal is a security answer about *this* connection, decision-0005 item 1: "a
     consumer that reconnects must verify again," not a transient state worth
     retrying) or `timeout_s`'s deadline passes, at which point the last
     `ChannelNotReady` is returned. `jail.channel_namespace_fd is None` (no channel
     declared) is a caller precondition violation, documented, not given its own
     exception type.

     `tests/integration/fakes.py`, mirroring `FakeSupervisors`'s shape) scripts a
     sequence of `ChannelNotReady`/`ChannelReady`/`ChannelRefused` returns; proves

### Risks
- **The outer-bwrap-pid-vs-in-jail-PID-1 distinction (step 1) is the single easiest
  thing to get wrong**, and the easiest to *silently* get wrong, since a test that
  only ever runs the "own listener" happy path would still pass with
  `jail_pid1_namespace`'s scan skipped and `Jail.process.pid`'s own `ns/pid` used
  directly instead -- it would just always compare bwrap's own (host) namespace
  against bwrap's own (host) namespace and call that "verified." Only the planted-
  symlink case (AC#2's actual refusal case) would catch this, which is exactly why
  that case is not optional -- it is the test that proves the scan happened at all,
  not only that refusal logic works.
- `getsockopt(socket.SOL_SOCKET, SO_PEERPIDFD)`: the constant may not exist as
  `socket.SO_PEERPIDFD` on every interpreter this project's floor (3.15) could run
  on -- the probe itself falls back with `getattr(socket, "SO_PEERPIDFD", 77)`. Keep
  that fallback, but an `AttributeError`-shaped gap is not what AC#5 means by
  "kernel without `SO_PEERPIDFD`" (that is an `OSError`/`ENOPROTOOPT` at call time,
  on a real kernel lacking the syscall) -- both collapse to the same
  `ChannelRefused(KERNEL_UNSUPPORTED)`, but say so explicitly in `channel_ready`'s
  own docstring so a future reader does not conflate "we hardcoded the wrong magic
  number" with "the kernel genuinely lacks this."
- AC#2's battery can only be *measured* passing on Linux with bwrap (CI). This
  session's host (macOS) can prove the code is written and structurally sound and
  that `just done` stays green, never that the battery's own assertions hold --
  state that distinction plainly when reporting this task's proof, the same way
  TASK-0001.26's own e2e batteries already distinguish "skipped cleanly" from "ran
  and passed."
- `jail_pid1_namespace`'s poll (step 2) needs its own bounded deadline distinct from
  `await_channel_ready`'s: a channel-declaring jail whose supervisor fork never
  produces an in-jail PID 1 that bwrap can find (should not happen with
  `--as-pid-1`, but nothing currently proves it cannot) must not hang
  `create_bwrap_jail` -- picking that deadline (and whether it is a fixed internal
  constant, like `_DEFAULT_WAIT_TIMEOUT_S`, or caller-supplied) is this task's own
  decision to make, not deferred.

Carried from TASK-0001.26's review (2026-10-25), two findings that land here rather than earning tasks of their own:

THE CRITICAL PROPERTY, CONFIRMED
jail_namespace_fd traces through the /proc children scan, never from Jail.process.pid's own namespace. The only assignment is api.py:683 namespace_fd = _namespace_fd_for(process, proc_root), whose body is:
    outcome = _sockets.jail_pid1_namespace(
        process.pid, time.monotonic() + _sockets.JAIL_PID1_TIMEOUT_S, proc_root
    )
and infra/sockets.py:jail_pid1_namespace roots the scan at bwrap_pid and returns os.open on a CHILD's ns/pid:
    for child in _children(bwrap_pid, proc_root):
        try:
            if _nspid(child, proc_root).split()[-1] != "1":
                continue
            return os.open(f"{proc_root}/{child}/ns/pid", os.O_RDONLY)
_process.pid is the outer bwrap; the fd is a different process's namespace. Nothing anywhere compares Jail.process.pid's own ns/pid.
