## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
pypeeker_rules/brig.py's `_classify_header_bases` buckets a declared base by what the single-file binder resolved it to. A same-file IMPORT whose `imported_from` is not in `_EXEMPT_BASE_IMPORT_ORIGINS` goes to `disallowed`. That is right for a genuine project base (`from brig.domain.base import Mixin`) but wrong for an exempt base re-exported through a project module: `from brig.domain.shim import Protocol` has `imported_from = 'brig.domain.shim.Protocol'`, so a `class Port(Protocol)` fires 'inherits from a base that is not Exception, Enum/StrEnum or Protocol' while inheriting from exactly Protocol. A false positive -- the direction TASK-0002's review established this rule must never take, since a HEURISTIC finding fails --strict the same as a DECLARED one.

Verified empirically against the real rule via the CLI path (pypeeker index + check --strict, rules=["brig-class-forms"]): fixture `src/brig/domain/shim.py` = `from typing import Protocol`, `src/brig/domain/p.py` = `from brig.domain.shim import Protocol` / `class Port(Protocol)` -> FIRES. The direct form (`from typing import Protocol`) and the alias form (`from typing import Protocol as P`) are both clean, so the verdict again depends on import style. Within one file the two shapes are indistinguishable -- `brig.domain.shim.Protocol` and `brig.domain.base.Mixin` are the same fact -- so this needs either one hop of cross-module import resolution (follow a project module's own IMPORT symbols) or a configured allow-list of re-exporting modules, or a decision record saying it stays a review-time concern.

Latent, not live: `grep -rnE '^class [A-Za-z_][A-Za-z0-9_]*\(' src/brig/` shows every base under src/brig today is a direct, same-file-resolvable name, so `just gates` is clean by conformance. Found while reviewing TASK-0002's fix; the docstrings there described this case as a conservative false negative, which this task's evidence disproves (corrected in the same review).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented the one-hop (pypeeker's own CrossModuleResolver is transitive, so really "however many hops resolve_definition follows") fix rather than a decision record: pypeeker.dsl's project columns (column_of(DEFINITION_KIND), column_of(DEFINITION_NAME) -- pypeeker.dsl.columns) stay on the same row while consulting Corpus.resolver, unlike follow(...) which replaces the row and loses the class correlation this check needs. Verified empirically (scratch probe against a real indexed fixture) before implementing: resolve_definition for a re-exported `from typing import Protocol` (via a shim module) lands on the shim's own Protocol IMPORT symbol -- DEFINITION_KIND=SymbolKind.IMPORT, DEFINITION_NAME='Protocol' -- one node short of typing.Protocol itself, because typing is never part of this corpus. A genuine disallowed base (brig.domain.base.Mixin) instead resolves all the way to that class's own CLASS symbol. That is the exact signal the new rule part reads.

Changes in pypeeker_rules/brig.py:
- _classify_header_bases: the same-file-IMPORT-not-matching-_EXEMPT_BASE_IMPORT_ORIGINS case now reports `ambiguous` instead of `disallowed` (it is genuinely indistinguishable from a re-export within one file). _disallowed_inheritance (the existing inheritance-restriction rule part) no longer fires on this shape at all -- a new rule part replaces exactly the coverage it gave up.
- New trait `brig-class-forms-reexport-candidate`, keyed on an IMPORT symbol's own id (not the class's): is this import some class's header base of that ambiguous shape, and if so, which class (Trait.value is the owning class's symbol_id, not a bool, so the new rule part's message can still name the class).
- New rule part `_reexported_base_disallowed`: a project-reach Selection over imports(), using the new trait plus column_of(DEFINITION_KIND)/column_of(DEFINITION_NAME) to resolve the import across files and decide whether the resolution is one of rule 7's four exempt shapes.
- Registered as brig-class-forms's 4th MultiPartRule part; updated the stale message on the 3rd (_disallowed_inheritance) that described the old, wrong behavior.
- Updated the module docstring and _classify_header_bases's docstring to describe the real mechanism and its one honest residual gap: resolution stops at the first unindexed module, so a third-party package re-exporting something bound to one of the four exempt bare names (Protocol/Enum/StrEnum/TypedDict) would read the same as a stdlib one. Not applicable to brig's own real code today (brig imports only stdlib, decision-0001), but the rule itself does not verify that -- named honestly rather than leaned on.

Tests added to pypeeker_rules/tests/test_brig_rules.py (all via the CLI index+check --strict harness, same as every other planted-violation test here):
- test_brig_class_forms_fires_on_disallowed_inheritance_via_import: AC#2's literal shape (from brig.domain.base import Mixin / class Thing(Mixin)) -- now caught by the new rule part, not the old one.
- test_brig_class_forms_accepts_a_protocol_re_exported_through_a_project_module: AC#1's fixture (shim.py re-exports typing.Protocol; a class inherits through it) -- no longer fires.
- test_brig_class_forms_accepts_a_protocol_re_export_with_state: the same re-export base with self.x = 1 in __init__, pinning that moving this shape from disallowed to ambiguous does not manufacture a stateful-class finding (the same "cannot tell" treatment TASK-0001.18 established for an attribute-chain base).

Verification: just test-pypeeker-rules (25/25 pass, including the 3 new tests), just gates (clean against real src/brig -- no false positive or false negative against brig's own classes), just lint, just typecheck all pass.

One known, narrow residual: _stateful_outside_infra now also treats a same-file-import base of unresolved origin as ambiguous (suppressing the stateful check), which widens that check's own false-negative surface by the same one shape -- a class with a genuinely-disallowed import-reached base AND instance state outside infra/ now gets only the inheritance-restriction finding (via the new rule part), not also a stateful-class finding. The inheritance violation is still reported either way, so this is a reduction in finding count for a doubly-bad class, not a silent miss, and matches the existing accepted-gap shape (same as the attribute-chain base case TASK-0001.18 already established).
