   would be disproportionate to a size-2 task; Material integrates natively with
   mkdocstrings-python and mkdocs-likec4, which AC#3/#4 need anyway. Flagged for the owner to
   override if they feel otherwise. Tick the intent's open question once mkdocs.yml uses it.
2. pyproject.toml: add mkdocs-material, mkdocstrings-python==2.0.9, mkdocs-likec4==1.2.2 as
   dev dependencies (pinned per TASK-0001's reference section). mkdocs.yml: configure the
   theme, nav, and both plugins.
3. docs/: expand index.md; write glossary.md (decision-0001 rule 12 -- jail, jail type,
   process, step, plan, claim, evidence, grade, supervisor, driver, effect, embedder, each
   named once); start docs/spec/ with brig's ten laws section.
4. **Known blocker, not worked around**: AC#2 wants the ten laws carried verbatim from the

   placeholder instead of fabricated text; AC#2 stays partially unmet until the owner provides
   the source or sets up the reference.
5. mkdocstrings: wire the reference page into mkdocs.yml's nav against brig's public API
   (src/brig/__init__.py's re-exports); confirm it's generated at build time, never committed
   (site/ is already gitignored).
6. docs/architecture/: extend the existing minimal LikeC4 placeholder (brig + a generic
   "Embedder", built earlier) with mkdocs-likec4 embedding in a docs page; confirm
   `likec4 validate` and c4lint stay clean.
7. Confirm the LikeC4 MCP server (already configured in .mcp.json, pointed at
   docs/architecture) actually answers a real query in this session.
8. `just done` already runs the docs build and architecture lint (from TASK-0001.01); confirm
   `mkdocs build --strict` still passes with the new plugins and theme.

  be fiddly; first-pass config may need iteration under `--strict`.
- This task is low-stakes (docs/tooling, not runtime security code) -- review effort is
  default, not 'high', and steps that are genuinely independent (the reference page wiring
  and the LikeC4 embedding) run in parallel rather than sequentially.
