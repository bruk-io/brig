## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`create_bwrap_jail` (TASK-0001.27) captures the jail's own PID namespace fd
(`infra.sockets.jail_pid1_namespace`) only *after* `run(operations.create(...))`
returns -- which is after the supervisor (`program.py`, the in-jail PID 1) has
already started, and after the supervised command it forks may have *already
finished*. `program.py`'s own `_main()` returns -- and the process exits -- right
after it emits the `done` event, with nothing left for it to wait on. For a
supervised command that writes a couple of files and exits in milliseconds, the
in-jail PID 1 can be gone from `/proc` before the host-side scan ever finds it:
`jail_pid1_namespace` then polls its own full deadline and correctly reports
`JailPid1NotFound` -- `ChannelNamespaceNotFound`, deterministically, regardless of
how long that deadline is, since the process it is looking for is not merely slow
to appear, it is already gone.

Measured directly: TASK-0001.28's own battery (two fast-finishing jailed commands)
hit this deterministically on real bwrap, on `ubuntu-latest`'s own unprivileged
userns CI runner -- twice, including after raising `JAIL_PID1_TIMEOUT_S` from 5s to
15s, which changed nothing (the suite's own run time grew by exactly the expected
2x10s, proving the scan waited out its full window both times and still found
nothing). Never reproduced in a `--privileged` Docker container on different,
slower (QEMU-emulated) hardware -- consistent with a race whose outcome depends on
relative process speed, not a logic bug in the scan itself. Never hit by
TASK-0001.27's own readiness battery, whose jailed commands all loop, sleep, or
fork-and-reap forever and so never finish on their own.

Worked around, not fixed, in TASK-0001.28's own battery: its jailed command now
sleeps after writing rather than exiting, matching every other real-jail battery's
own pattern in this codebase. That is a reasonable thing for a battery to do
regardless, but it leaves the real gap open for any *production* embedder whose
supervised command is short-lived and who also declares channels -- exactly the
shape a real caller might reasonably want (a one-shot jailed script that happens to
write to a declared channel before exiting).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented 2026-10-25 (the cheaper option, agreed with @bruk): capture made robust to the command having finished, no supervisor change.
- infra.sockets: new JailPid1Exited sentinel; jail_pid1_namespace scans for the PID 1 first, then checks the outer process (`_gone`: no /proc entry, or State Z) and returns JailPid1Exited at once instead of waiting out the deadline. Outer process alive + no PID 1 stays JailPid1NotFound -> ChannelNamespaceNotFound.
- presentation: create_bwrap_jail returns a Jail with channel_namespace_fd=None and channel_directory set; await_channel_ready returns the new terminal ChannelJailFinished (exported) without connecting. A None fd with no channel_directory is still the ValueError precondition.
- Tests: tests/integration/test_channel_jail_finished.py (gone/zombie outer, readiness never asked, running jail still gets its fd); tests/e2e/test_channel_jail_finished.py (real bwrap `true` with a channel = AC#2; real-procfs scan tests).
Verified here (macOS): pytest unit+integration 76 passed, mypy, ruff, pypeeker gates. NOT verified: AC#2 (e2e skips without bwrap; CI must run it), the procfs e2e tests (skip on macOS), `just done`, docs, arch lint. AC#2 left unticked until CI is green. Not done: keep-alive supervisor (rejected as heavier; revisit only if an embedder needs a namespace fd for a finished jail).
