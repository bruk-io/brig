## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

An adversarial review of the walking skeleton (TASK-0001.03) found two hazards in infra's process
primitives that only appear in an embedder brig cannot see, and that decision-0001 does not name:

- infra/processes.py spawns with os.fork() and then runs os.setsid(), os.chdir() and os.execvpe()
  in the child. None of those is async-signal-safe: os.execvpe is Python code that builds the
  environment and walks PATH, so in a multi-threaded embedder the child can block on a lock another
  thread held at fork time. The parent then blocks forever on its os.read() of the error pipe, and
  the public API hangs with a forked clone of the embedder's process alive. Python 3.15 already
  deprecates fork in a multi-threaded process. posix_spawn or vfork-style exec is the usual answer.
- infra/processes.py's reap is an untimed os.waitpid. A jailed process that never exits hangs the
  embedder forever, and no effect in domain/effects.py expresses a wait with a deadline, so no
  operation can give up. A sandbox whose subject can block the host program indefinitely is a
  denial of service in the primitive, separate from the teardown ladder's own grace period
  (step 4's "the teardown ladder in full").
<!-- SECTION:DESCRIPTION:END -->

Full check `uv run just done` exited 0 (recorded above); it changed no files.

Independent verification of the two claims the review was asked to confirm:
- Spawn does not fork: no `os.fork` anywhere in src/ (only a docstring mentioning the old approach). infra/processes.py:98 uses `os.posix_spawnp(argv[0], list(argv), env, setsid=True)`. Verified live on this host: a missing binary raises SpawnError (ENOENT surfaced as OSError from posix_spawnp, so there is no error-pipe read that can block), and a spawned process is its own session leader (getsid(pid)==pid). No parent read of a child pipe remains, so AC#1's second clause holds.
- The deadline wait cannot block forever: `reap_deadline` polls WNOHANG and returns None once `deadline - monotonic() <= 0`. Verified live: a 0.3s deadline on `sleep 30` returned None in 0.301s; an already-past deadline returned None in 0.000s; ECHILD returns ProcessUnknown, kept distinct from None.
- AC#2: `Reap(process, deadline)` is an effect in domain/effects.py, `operations.start(..., deadline=)` carries it, and presentation/api.py `run_jail` turns None into JailWaitTimedOut and ExitCodeUnknown into JailExitUnknown. No infra type crosses the port.
- AC#3: tests/integration/test_wait_deadline.py covers the expiry mapping through FakeProcesses; the substance of a deadline genuinely expiring is tests/e2e/test_processes_gateway.py::test_reap_deadline_returns_none_on_a_genuine_timeout_not_process_unknown, which passed on this host. tests/e2e/test_bwrap_journey.py::test_bwrap_process_never_exits_times_out runs the full journey for `sleep 9999`; it skips on macOS (expected) and runs in CI (ubuntu-latest, installs bubblewrap).

Findings, none blocking, none filed as a new draft:
- Low: `os.posix_spawnp(..., setsid=True)` raises NotImplementedError, not OSError, on a platform without POSIX_SPAWN_SETSID. `spawn` catches only OSError and the bwrap driver catches only (SpawnError, OSError), so on such a host a non-brig exception escapes the public API. Belongs on queued TASK-0001.08 ("Let no raw OSError escape..."), the same area, rather than a task of its own.
- Known residual, out of scope by the task's own wording: teardown's post-KILL `Reap(process)` is still deadline-less, so it reaches infra's unbounded `os.waitpid`. It is the only such path (domain/teardown.py:73, the one site). The description carves it out and queued TASK-0001.07 owns the bounded grace period for multi-process groups.
- Note, no action: `run_jail` now defaults to a 30s timeout with no way to express an unbounded wait, a semantics change for a legitimately long-running jailed command.
