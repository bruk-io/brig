## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during adversarial review of TASK-0006/0009 (fixed in that same review pass: `src/brig/domain/jail_types/bwrap.py`'s module docstring and `src/brig/presentation/api.py`'s `_supervisor_path` docstring have been narrowed to state only what is measured; this task tracks the residual *behaviour* gap those docstrings now describe instead of claiming it away).

`compile_supervisor_launch`'s unconditional `--ro-bind state_dir state_dir` lands in the compiled argv after the caller's own `policy` binds, so it can never be *shadowed* by an exact-path-overlapping policy bind (`tests/e2e/test_fs_policy_battery.py::test_a_policy_bind_at_the_state_dirs_own_jail_path_does_not_shadow_it` already covers that). But "cannot be shadowed at the exact path" is not the same claim as "reachable under every policy", and TASK-0006's AC#1 ("regardless of the caller's fs policy") and the two docstrings both said the broader one.

Measured for real against bwrap in `brig-probe-amd64:latest` (BRIG_HOME set to an otherwise-untouched `/custom/brig-state`, so the result is not confounded by `uv`'s managed CPython also living under `/root`):

- A writable ancestor bind at `/custom` (source empty, lacking the leaf) -- jail starts, exit 0.
- A read-only ancestor bind at `/custom` whose source *does* contain the leaf (`brig-state/`) -- jail starts, exit 0.
- A read-only ancestor bind at `/custom` whose source does *not* contain the leaf -- `bwrap: Can't mkdir /custom/brig-state: Read-only file system`, then `JailExitUnknown` (and, per the original finding, `JailTeardownFailed` on the following `destroy_jail`).

So the real gap is narrow and precise: a *read-only* ancestor bind of the state directory, sourced from somewhere that does not already contain the state directory's own leaf, breaks every jail under that policy -- the "give the jail a clean fake home" shape (e.g. `Bind(host_path=<empty tmpdir>, jail_path='/root')`) is an entirely ordinary policy to want, and currently breaks every jail that uses it if `BRIG_HOME`/`~/.brig` falls inside that ancestor.

Root cause (not yet fixed): bwrap builds each bind's mountpoint by creating any missing directory components in the new root *before* applying that bind's own mount, in argv order. By the time the unconditional state-dir bind runs, the ancestor bind already occupies that subtree read-only, so creating the missing `state_dir` leaf directory inside it fails with `EROFS`. Reordering the two binds does not obviously help: mounting the ancestor bind *after* the leaf would instead shadow/hide the already-mounted leaf (Linux mount semantics: a later mount at a path replaces the entire view beneath it), which is exactly what the "does not shadow" test above already guards against happening the other way.

Candidate directions, unexplored here (next task picks one and measures it against real bwrap before committing):
- `--dir <state_dir>` (bwrap's own explicit-directory-creation flag) issued ahead of the ancestor bind, if bwrap's directory creation is not itself revoked by a later read-only mount over an ancestor -- plausible but unverified; may hit the identical `EROFS` at the same step.
- Giving the state dir its own, always-topmost jail path (e.g. a fixed `/brig-state` at the jail's root, parallel to `/`, rather than nested under wherever the host's real `BRIG_HOME` happens to live) so no caller-named ancestor bind can ever cover it structurally, regardless of `BRIG_HOME`'s own value.
- Documenting the constraint instead of lifting it: require a caller whose policy covers the state directory's own ancestor read-only to also explicitly include the leaf (or move `BRIG_HOME` outside that ancestor), and have `create_bwrap_jail` or `_resolved_state_dir` detect and refuse that combination loudly instead of surfacing as `JailExitUnknown`/`JailTeardownFailed`.
