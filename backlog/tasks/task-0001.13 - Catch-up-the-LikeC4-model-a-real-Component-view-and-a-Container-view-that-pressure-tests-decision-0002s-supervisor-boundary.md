## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
### Order of work

1. Component view: docs/architecture/models/brig/ gains components for domain's real modules
   (effects, operations, teardown, plan, jail_types.bwrap), infra's (processes), and
   presentation's (api, errors, ports, drivers.bwrap), inside the existing "brig" software
   system. Relationships follow decision-0001 rule 1 exactly (presentation knows both,
   domain/infra know neither brig layer).
2. Container view (new): split "brig" into containers for the first time -- the library
   itself (runs inside the embedder's process) and a `supervisor` container, tagged
   `#planned` (decision-0002, not yet built), with the wire-protocol relationship between
   them. This is the actual design-validation step: if the boundary reads wrong once drawn,
   that is a finding for decision-0002, not a diagramming problem to paper over.
3. Run `likec4 validate` and c4lint; fix until clean. Confirm `just done`'s architecture
   steps still pass.
4. Report back anything the modeling surfaced about decision-0002's shape specifically --
   that is the point of doing this now rather than after the supervisor is built.

### Risks

- A `#planned` container inside an otherwise-real model is a deliberate, supported pattern
  (the scaffold's own `_spec.c4` ships a `planned` tag), but it is non-standard C4 in the
  sense that most Container views show only what exists. Worth being honest in the view's
  title/description that one box is a plan, not a fact, so a reader does not mistake it for
  shipped.
- c4lint's black-box rule (never reach into another system's internals) and its
  one-abstraction-level-per-view rule both get a first real test here, since this is the
  first Container-level view in the model.

### Proof

- `likec4 validate` clean, c4lint 0 errors.
- The Component view's elements match `find src/brig -name "*.py" -not -name "__init__.py"`
  exactly.
