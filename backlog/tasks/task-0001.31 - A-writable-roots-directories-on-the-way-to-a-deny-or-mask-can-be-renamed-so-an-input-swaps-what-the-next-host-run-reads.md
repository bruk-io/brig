## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The old brig (old SPEC decision-168) bound every existing directory between a writable root and a write deny or mask over itself, so rename(2) inside the jail fails with EBUSY. compile_mounts does not: inside a writable root W with a deny at W/a/b/f, the jailed process can rename W/a (or W/a/b) away and create its own W/a/b/f, which the host reads once the jail is gone. The deny protects the inode it was mounted on, not the path the host reads. Found by an embedder's swap onto brig (four strict-xfail tests there plant it: a directory on the way to the interpreter, to a git config, to a layer file).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 compile_mounts binds each existing directory strictly between a writable root and a write deny or mask over itself, with the root's own writability, ordered so the deny or mask still lands on top
- [ ] #2 An e2e battery renames each such directory inside a real bwrap jail and fails if any rename succeeds; recorded failing before the fix
- [ ] #3 fs_write's ceiling and the spec say what the pin covers (renames of existing directories) and what it does not (a directory created after the jail starts)

Implementation (commit a4cd4df, repro 9f207dd): domain/jail_types/bwrap.py compile_mounts now adds a pin, a writable bind of the directory over itself, for each directory strictly between a writable root and a kept write deny or mask, where the jail shows it writable (_governing_role is writable) and it is no policy entry (an entry is a mount point already). Pins sort with everything else by depth, so each lands after its root and before the deny or mask it leads to. A directory is pinned when it is one on the host (kinds) or, on the way to an absent deny or mask, when it is absent too: brig's placeholders make it before the jail starts. pin_candidates(policy) names the paths to look up; presentation/drivers/bwrap.py gets their kinds through infra/files.py facts, so the domain stays pure. Measured in a real jail: renaming a pinned directory fails with EBUSY, and a rename from a pinned directory to the rest of its root fails with EXDEV (the cost, written in the SPEC). FS_WRITE_CLAIM's description, the ceilings docstring and docs/spec/index.md say what is covered (a rename from inside the jail of a directory there when it started) and what is not (the host itself creating, removing or renaming one while the jail runs). Tests: tests/e2e/test_pin_rename_battery.py (a deny on a file, a mask on a directory, an absent deny under an existing and under a missing parent; a control rename beside them; held to the fs_write ceiling with at_most) and two unit tests in tests/unit/test_fs_policy_compile.py. Not verified: a writable_shared_paths caller that minds the pins being listed (each is inside a writable root already listed, so channel_exclusivity does not change); an editor or tool in a real embedder that renames across a pinned directory and now gets EXDEV. Out of scope, seen: a readable root nested in a writable root has the same rename hole (renaming its parent moves the read-only mount, and the command can make its own content at that path); pins cover only denies and masks.

Measured after the fix, out of scope: with readable roots ('/', W/z/r) and writable W, a jail renamed W/z to W/z-moved, made W/z/r/tool, and the host then read 'planted' there. A readable root nested in a writable root needs the same pins; not fixed here.
