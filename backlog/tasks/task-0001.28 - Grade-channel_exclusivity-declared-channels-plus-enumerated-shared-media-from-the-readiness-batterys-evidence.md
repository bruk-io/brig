## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
### Order of work
1. `domain/jail_types/bwrap.py` gains the claim and the two pure functions that
   state it -- no change to `compile_supervisor_launch`'s own signature or return
   value, which stays exactly as `tests/unit/test_bwrap_compile.py`'s byte-exact
   assertion already pins it (that assertion is load-bearing evidence for
   TASK-0001.16; this task does not touch it or that function's return type).
   - `CHANNEL_EXCLUSIVITY_CLAIM = Claim(name="channel_exclusivity", description=...)`,
     a public module-level constant -- "bwrap's compile states a claim" (AC#1) means
     the claim's own `Claim` value comes from this module, the way `claims.py`'s own
     docstring asks for, not from a test file inventing one independently (the
     existing `FD_INHERITANCE_CLAIM`/`TIOCSTI_CLOSURE_CLAIM` precedent in
     `tests/e2e/test_claims_wiring.py` does the latter -- decision-0002 item 4 calls
     that pattern acceptable for a battery wiring a claim *in*, but AC#1's own
     wording for this task is stronger: the claim itself must come from bwrap's own
     module). Import `Claim` from `domain.claims` -- a domain-internal import,
     unlike a cross-jail-type one, so this does not need to touch `brig-slices`'s
     own allow-list.
   - `writable_shared_paths(policy: FsPolicy, state_dir: str, channels: Reservations | None) -> tuple[str, ...]`:
     the enumeration AC#2 asks for ("every path the jail can write that the host can
     also reach"). **Do not filter `policy.binds` on `Bind.writable` in isolation** --
     that is the wrong predicate, and it is wrong for the exact reason this session
     already measured on real bwrap: `compile_supervisor_launch` emits the channel
     bind *writable*, nested *inside* the state-dir bind's own *read-only* mount,
     later in argv, so it wins (the "writable channel bind inside the read-only
     state-dir bind" property TASK-0001.26/.27's own CI run just confirmed for
     real). Build the exact same compiled bind sequence
     `compile_supervisor_launch` builds, in the same order --
     `(*policy.binds, Bind(host_path=state_dir, jail_path=state_dir),
     *((Bind(host_path=channels.directory.host_path,
     jail_path=channels.directory.jail_path, writable=True),) if channels is not
     None and channels.reservations else ()))` -- then, for every *candidate* path
     in that sequence (each bind's own `jail_path`), find the *last* bind in the
     whole sequence whose own `jail_path` either equals that candidate or is a
     strict ancestor of it (the same "later wins, nested or exact, argv order"
     reasoning `covering_ancestor_bind` already encodes for the strict-ancestor
     case -- generalise it to include the exact-match case too, rather than calling
     it twice or re-deriving the scan by hand) -- that bind's own `writable` flag is
     the candidate's *effective* writability. Return the distinct candidate paths
     that come out writable. This is why the state-dir bind belongs in the
     enumeration at all (AC#2 names it explicitly): it is always a *candidate*
     (always present, unconditional), and it is this function's own job to prove it
     never comes out writable on its own exact path, even though a nested channel
     bind right next to it does.
   - `declared_channel_paths(channels: Reservations | None) -> tuple[str, ...]`:
     `()` if `channels` is `None` or declares nothing; otherwise
     `(channels.directory.host_path,)` -- the channel *directory* is what the bind
     actually targets (`_compile_channel_bind`'s own shape), not each reservation's
     individual file inside it.
2. `brig/__init__.py`: export `CHANNEL_EXCLUSIVITY_CLAIM`, matching how
   `WHOLE_HOST_READ_ONLY` is already exported from `domain.policy.paths`.
3. `tests/unit/test_channel_exclusivity_claim.py` (new): pure, no I/O, for
   `writable_shared_paths`/`declared_channel_paths` against plain `FsPolicy`/
   `Reservations` data (no real jail, no real filesystem) --
   - no channels, default policy -> `writable_shared_paths` is `()` (neither the
     root bind nor the state-dir bind is writable on its own).
   - channels declared, default policy -> exactly the channel directory's own
     path, nested inside the read-only state-dir bind -- the one case that proves
     the "later wins" reasoning runs at all, not just a `.writable` filter (a wrong
     implementation using a bare filter would *also* pass this one accidentally,
     since the channel bind genuinely is `writable=True` -- case 4 below is the one
     that actually discriminates).
   - channels declared, policy *also* names an unrelated writable `Bind` -> both
     paths come back.
   - a writable policy `Bind` that a *later* read-only policy `Bind` shadows at an
     ancestor path -> excluded: the discriminating case against a bare
     `.writable` filter, which would wrongly include it.
   - the state directory's own path is never in the result, regardless of what
     channels declare (AC#2's own explicit mention of it).
4. `tests/e2e/test_channel_exclusivity_claim.py` (new), mirroring
   `test_claims_wiring.py`'s own shape (a claim constant imported from where it is
   actually stated, evidence measured directly against something real, `grade`
   called at the end) -- against real bwrap (`skipif(shutil.which("bwrap") is
   None, ...)`, same guard every other real-jail battery uses):
   - **Control**: a real jail declaring one channel, no other writable bind. The
     jailed command writes a known string into a file inside its own channel
     directory; after `destroy_jail`, the host reads it back -- proof the control
     is real, not merely computed from policy data. `writable_shared_paths` on this
     jail's own `policy`/`state_dir`/`channels` returns exactly the channel
     directory's path, matching `declared_channel_paths` exactly ->
     `Evidence(control_observed=True, violation_blocked=True)` -> `grade` reports
     `ENFORCED`.
   - **Violation**: a real jail declaring the same one channel, *plus* an extra
     writable `Bind` in its own `FsPolicy` pointing at a throwaway host directory
     unrelated to any channel. The jailed command writes into *both* -- the channel
     directory (still the control signal) and the extra bind (the "shared media"
     leak) -- and the host reads *both* back after `destroy_jail`, proving the
     extra path is a real, exploitable leak, not a hypothetical one from policy data
     alone. `writable_shared_paths` now returns two paths; `declared_channel_paths`
     still names only the channel -> `Evidence(control_observed=True,
     violation_blocked=False)` -> `grade` reports **`VIOLATED`, not
     `UNENFORCED`**: the control fired (we know the probe can see a real writable,
     shared path), and the planted extra path genuinely was not blocked -- AC#2's
     own "does not grade enforced" is satisfied by either `VIOLATED` or
     `UNENFORCED`, but only `VIOLATED` is the honest word for "we measured a real
     leak", and `UNENFORCED` would understate what was actually found.
   - No change to `domain/grades.py`: `grade()` is already generic, already fully
     unit-tested, and needs nothing new to grade this claim correctly -- this task
     only produces the `Claim` and the `Evidence` a correct call already handles.

### Risks
- The whole claim is hollow if `writable_shared_paths` is implemented as a bare
  `[b.jail_path for b in policy.binds if b.writable]` filter: it would pass the
  "channels declared, default policy" unit test by coincidence (the channel bind
  really is `writable=True`) while never actually reasoning about argv order or the
  unconditional state-dir/channel binds `compile_supervisor_launch` adds outside
  `policy.binds` entirely. The shadowed-writable-bind unit test (step 3's fourth
  case) is what catches this -- it must not be skipped or weakened.
- `writable_shared_paths` needs the exact same compiled-bind-sequence shape
  `compile_supervisor_launch` builds. If that function's own argv order ever
  changes, this enumeration silently stops matching reality the same way
  `_check_channel_directory_reachable` (TASK-0001.26) already depends on it --
  cross-reference both in this new function's own docstring rather than re-deriving
  the ordering fact a third time.
- The e2e violation case must actually demonstrate the leak (a real write/read
  through the extra bind), not merely assert that the *policy* names one -- a
  policy-only version of this test would not be e2e at all, and would not prove the
  enumeration's answer corresponds to anything real.
- Use the Docker route (`brig-probe-amd64:latest`, now that CI billing is also
  fixed) to actually run the new e2e battery during implementation, not only after
  pushing -- that is what caught three real bugs on TASK-0001.27 that a macOS-only
  pass could not have.

### Correction (post-review)
- **Path-space ambiguity in `writable_shared_paths`, resolved**: candidates are
  identified in *jail-path* space (that is what "which bind governs this location"
  -- the `covering_ancestor_bind`-style reasoning -- is actually about), but the
  value this function *returns* for each writable candidate is the *host-side*
  location of whatever bind actually governs it there, computed the same way
  `presentation/api.py`'s `_check_state_dir_reachable`/`_check_channel_directory_reachable`
  already compute a "host equivalent" for a nested path: given the governing bind
  `g` for candidate `c` (in jail-path space), the host-side path is
  `g.host_path.rstrip("/") + c[len(g.jail_path.rstrip("/")):]` -- the empty-suffix
  case (`c == g.jail_path` exactly) is every candidate this task's own test cases
  and the one real production shape (the channel bind, host_path == jail_path by
  `ChannelDirectory`'s own stated invariant for bwrap today) actually produce, but
  the formula is written in general rather than assumed, the same discipline
  `covering_ancestor_bind`'s own docstring already states for itself. Only compute
  this for a candidate whose governing bind is writable -- an excluded (non-writable)
  candidate's host-side location is never needed. `declared_channel_paths` stays in
  host-path space (`channels.directory.host_path`) to match what this function now
  returns, so the two are directly comparable without a second translation anywhere
  else.
- **Worker instruction**: build the compiled bind sequence by reconstructing it from
  `policy`/`state_dir`/`channels` directly, in the same order
  `compile_supervisor_launch` builds it -- never by calling
  `compile_supervisor_launch` itself and parsing its own argv strings back apart.
  Parsing flags back out couples this function to exact flag text and breaks the
  moment `_VIRTUAL_FS_FLAGS` or anything else shifts position in that argv; this
  function reconstructs the same *data*, from the same inputs, not the rendered
  output.
- **Step 4's control is read in the wrong order, fixed**: `destroy_jail` removes
  the channel directory (`directories.remove`, `shutil.rmtree` -- TASK-0001.26/.27's
  own cleanup). The control's file must be read back *before* `destroy_jail` is
  called, not after -- reading after would make the control itself report nothing
  there, for a reason that has nothing to do with the claim, and (since the extra
  bind's own path sits *outside* the channel directory and survives) the violation
  case would still pass while the control failed, misreporting `UNENFORCED` for the
  wrong reason entirely. The extra-bind write (the violation case) may still be read
  after `destroy_jail`, since that path is untouched by the channel directory's own
  cleanup -- but read it before too, for symmetry, since there is no reason not to.
