## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implementation: `domain/policy/env.py` adds `EnvPolicy` (an allow-list by name, mirroring `FsPolicy`'s shape) and `scrub_env(host_env, policy) -> dict[str, str]`, pure, plus `DENY_ALL` as the default policy (nothing passed through -- the same safer-default reasoning `Bind.writable=False` already gives filesystem binds). `operations.create(plan, policy=DENY_ALL)` is `scrub_env`'s one caller: it filters `plan.env` (the jail type's own candidate environment, `Plan.env`'s own docstring -- not yet scrubbed) down to `policy.allowed` before building the `StartSupervisedCommand` effect, so the effect's own data is already scrubbed and nothing performing it (a driver, or `infra/supervisor/link.py`/`program.py` underneath one) ever reads `os.environ` itself to get there. Confirmed by reading `program.py`'s `_start_child` (`os.posix_spawnp(argv[0], argv, env)`, explicit env, never inherited) and `link.py`'s `_start` (the same `env` the effect carries reaches both the wire's exec request and the supervisor's own spawn) -- the scrubbed value genuinely reaches the exec, this is not inert plumbing.

Settling TASK-0001.15's own open question (its Implementation Notes: env's one representation across both tasks): `scrub_env` returns a plain `dict` (no `frozendict` on this interpreter, TASK-0001.15's own measured finding, noted again in `scrub_env`'s docstring); `operations.create` is the one place that converts it to the `tuple[tuple[str, str], ...]` `StartSupervisedCommand.env` already carries.

Out of the two listed `modified_files`, also touched: `plan.py` (the `Plan.env` docstring was stale after this -- it previously implied TASK-0001.17 would populate it directly; corrected to say `operations.create` scrubs it, and a jail type's compile still never reads the policy, rules 2/3), `domain/policy/__init__.py` (its own docstring said env.py was 'a later addition'), and `presentation/api.py`/`src/brig/__init__.py`. The api.py change was necessary, not optional scope-creep: `tests/integration/` may only import brig's public API or `tests.integration.fakes` (pypeeker `brig-test-layers`, decision-0001 rule 4), so proving via `FakeSupervisors` that the *scrubbed* env -- not a host-like candidate -- reaches the supervisor's `start` call requires a public entry point that accepts both an `env` candidate and an `EnvPolicy`. Added `env`/`env_policy` keyword params to `create_bwrap_jail`, defaulting to `()`/`DENY_ALL` (unchanged behaviour for every existing caller), and re-exported `EnvPolicy`/`DENY_ALL` from `brig/__init__.py` alongside `FsPolicy`'s own precedent. brig still never reads `os.environ` anywhere -- that remains a caller's own choice to wire, same as before this task, now reachable rather than dead-ended.

Tests: `tests/unit/test_env_policy.py` (5 cases: allow-list filtering, no fabrication, DENY_ALL, determinism/key-order, no mutation of either argument) + one case added to `tests/unit/test_bwrap_compile.py` driving `create`'s generator by hand with a non-default policy, pinning that a disallowed name never reaches the yielded effect. `tests/integration/test_env_scrubbing.py` (2 cases): a host-like `env` + a narrow `EnvPolicy` through `create_bwrap_jail`/`FakeSupervisors` shows only the allowed name in `supervisors.started`; a second case pins `DENY_ALL` as the default even when a host-like `env` is given, so a caller naming no policy never gets a silent pass-through.
