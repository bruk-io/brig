## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

TASK-0001.01's gate implements decision-0001's rules 1-7, 12 and 14, but three of the 8 custom
pypeeker rules only partially enforce what the decision text says, for reasons documented in
pypeeker_rules/brig.py and TASK-0001.01's implementation notes:

- brig-class-forms only catches @dataclass without frozen=True. pypeeker's DSL exposes no
  base-class/inheritance facts at all (no `bases` field on a symbol, no corpus access from an
  opaque predicate, no way to register a new column) -- so Protocol/Enum/Exception classification,
  the "no inheritance but Exception/Enum/Protocol" restriction, and "a stateful class only in
  infra/" are not mechanically enforced.
- brig-one-writer misses `from sys import stdout; stdout.write(...)` -- only the `sys.stdout.write`
  receiver-chain form is caught.
- brig-pure-domain's heuristic half (`no-impure-functions` with `include=["brig.domain*"]`) is
  configured but unverified: it's a no-op on the still-empty skeleton, so whether it actually fires
  on a real impure domain function is unknown until one exists.

## Open questions

- [ ] Is pypeeker worth extending (a `bases` fact, a `register_column` hook) to close the
  class-forms gap, or does this stay a review-time concern forever? Carried forward: a real
  decision once real domain classes exist to test it against.
- [ ] Does the one-writer gap matter in practice, or is `sys.stdout.write(...)` the only form
  brig's own code style would ever produce? Carried forward: revisit once infra/log.py exists.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
AC#1 (brig-class-forms classification + inheritance): implemented, not deferred to a decision
record. Re-checked the currently-installed pypeeker (git main, unpinned) against brig.py's own
claim and found it only half true: the symbols() universe still has no `bases` field, COLUMNS is
still closed with no register_column, and Opaque.evaluate still only sees ctx.row -- so a where()
clause alone really cannot ask "does this class inherit from X", confirming the original note.

But there's a second, real plugin surface the prior note missed: pypeeker.analysis.register_trait
registers a hand-written provider with signature (file_index, symbol_id) -> Trait -- the whole
FileIndex, not a row's declared fields -- and pypeeker.dsl.trait_of(name).value is a genuine
where()-clause read of it. Confirmed empirically (probe script against a planted fixture, loading
the index via pypeeker.storage.IndexStore) that a class's declared-base header reference resolves,
within one file, to <builtins>.Exception for a bare `Exception` base, or to the same-file IMPORT
symbol for `Protocol`/`Enum`/`StrEnum`, whose own `imported_from` field names the qualified origin
-- the same "follow imported_from" technique brig-one-writer and brig-pure-domain already use
elsewhere in this file. No source-text parsing and no cross-module resolver needed for the common
case.

Implemented as a new trait provider (`brig-class-forms-disallowed-base`, registered directly via
register_trait, not via the DSL's trait() composition helper, which refuses PROJECT reach and is
boxed into the symbols() universe's declared fields) plus a second RulePart on `brig-class-forms`
quantifying over symbols() with trait_of(...).value.eq(True). Reports Confidence.HEURISTIC rather
than DECLARED when a base can't be resolved within the one file (an attribute-chain base like
`import typing as t; class C(t.Protocol)`, or a re-export through another module) -- a narrow,
documented, accepted gap of the same kind brig-one-writer's aliased-module-import gap already is.
Does NOT cover "a stateful class only in infra/" (a question of where a class lives, not what it
inherits -- out of AC#1's wording) or multi-hop/transitive base chains.

Updated pypeeker_rules/brig.py's module docstring to stop claiming "there is no way around the DSL
surface either" -- that line was stale/overstated once register_trait is accounted for.

(test_brig_class_forms_fires_on_disallowed_inheritance, plus
test_brig_class_forms_accepts_a_protocol_subclass/an_exception_subclass/an_enum_subclass as
negative checks that the three exempt forms don't false-positive). Added an assert_rule_clean

Adversarial review on AC#1/#2 found two blocking issues, now fixed:

1. The 15 (now 16) pypeeker_rules/tests tests -- the evidence for all three ACs -- ran under no gate and no CI: run_done.py's step list never reached them, and just check's affected_tests.py only selects tests/unit and tests/integration. Fixed by adding a 'test-pypeeker-rules' just recipe and a 'pypeeker rule tests' step in run_done.py (just check's affected_tests.py still does not reach pypeeker_rules/tests -- a separate, narrower gap left as-is).

2. brig-class-forms-disallowed-base false-positived on conforming code with no suppression path: 'import typing as t; class C(t.Protocol)' flagged '[brig-class-forms]' and failed just gates, because the Implementation Notes' characterization was wrong on two counts -- it called an over-flagging bug 'the same kind of gap' as brig-one-writer's under-reporting gap, and the actual root cause wasn't really the single-file resolution limit as described: an attribute-chain base's receiver root (here, the 't' import symbol) was itself being read as if it were the declared base, and a module import's imported_from ('typing') never matches the exempt list ('typing.Protocol'), so the chain's root always disallowed regardless of what it's an attribute of. Fixed by (a) filtering out any reference consumed as another reference's receiver_root_symbol_id before evaluating candidate bases, and (b) reporting value=False (not a guessed True at HEURISTIC) for a base this file genuinely cannot resolve, since a HEURISTIC finding still fails the gate under --strict. Added test_brig_class_forms_accepts_a_protocol_subclass_via_attribute_chain as a regression test (17 tests now, all passing under the new gate).

The notes above (written before this review round) still describe the pre-fix HEURISTIC-guess behavior and the 14/4 test count; this comment supersedes that paragraph and the stale count. just done passes clean.
