## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0006 moved the supervisor's assembled script off `/tmp` into brig's own state directory (`infra/state_dir.py`, default `~/.brig`, overridable via `BRIG_HOME`) so a caller's narrow `FsPolicy` can no longer break the jail. That fix traded away a property `/tmp` gave for free: on most hosts something else (systemd-tmpfiles, macOS's periodic cleanup) eventually collects old files left there. Nothing sweeps `~/.brig`.

`presentation/api.py`'s `_supervisor_path()` still writes with `tempfile.NamedTemporaryFile(..., delete=False)` and is `functools.cache`d, so every process that creates at least one jail leaves exactly one `brig-supervisor-*.py` behind in the state directory, forever. Measured directly on this host after ordinary development/test activity (not a stress test): `ls ~/.brig | wc -l` -> 8 files already, from this session's own `just done` runs and container-adjacent local test runs alone. An embedder that starts short-lived processes repeatedly (a CLI invoked per command, a worker restarted per job) grows this directory without bound, with nothing in brig itself to notice or cap it.

Out of scope for TASK-0006 itself: its plan and acceptance criteria are about reachability under a narrow fs policy, not retention, and the plan names no cleanup mechanism.</description>
<parameter name="acceptanceCriteria">["A supervisor script this process wrote to the state directory is removed once nothing can still need it (e.g. on normal process exit, or swept by a later process on `resolve`/`ensure` once old enough to be safely considered abandoned) -- stated explicitly, since `/tmp`'s own cleanup no longer does this implicitly", "A test plants a stale supervisor-script-shaped file in the state directory and asserts it is gone (or is swept) under whatever mechanism is chosen, without deleting a file still in use by a live jail in the same run", "A test demonstrates no unbounded growth across many jail creations in one process (the existing `functools.cache`d single-file-per-process behavior is not changed silently without this being re-measured)"]
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Each jail's own assembled supervisor script is deleted by destroy_jail, exactly once teardown has verified the jail's process group is gone (GroupState.GONE) -- never before that confirmation, and never left for a sweep or atexit hook (narrowed from the original filing's open candidates: destroy_jail's own existing GONE verification is an already-safe, already-called deletion point that needs no new wire-protocol signal)
- [x] #2 create_bwrap_jail no longer writes one supervisor script shared (functools.cache'd) across every jail a process creates -- each jail gets its own freshly-written file, computed exactly once per jail and threaded consistently to both the compiled bwrap argv that actually launches it and the Jail value destroy_jail later deletes by
- [x] #3 A test proves a jail's own supervisor script is gone from the state directory after its destroy_jail call returns successfully
- [x] #4 A test proves destroying one of two jails created by the same process does not delete the other, still-live jail's own file, and that the other jail still runs correctly afterward
- [x] #5 A test proves many create/destroy cycles in one process leave zero accumulated files in the state directory afterward, not merely bounded growth
- [x] #6 tests/integration/test_destroy_without_run.py's existing shape (destroy called before run) still cleans up its own file correctly

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
### Design (settled with the owner)
destroy_jail's own teardown already verifies GroupState.GONE before returning
without raising -- proof, with no new signal needed, that nothing from that jail
will ever read its supervisor script again (the only genuine danger is deleting
*before* a confirmed-safe point, mirroring TASK-0001.22's own exec-timing-race
finding; deleting *after* GroupState.GONE has none of that risk, whether or not
the script was ever actually exec'd). This only works cleanly if each jail has
its own file: the current functools.cache'd _supervisor_path()/_supervisor_argv()/
_live_supervisors() singletons share ONE file across every jail a process
creates, so deleting on the first jail's destroy would break every later one.

### Order of work
1. presentation/api.py: remove @functools.cache from `_supervisor_path()` --
   every call writes a genuinely fresh NamedTemporaryFile into the (still-cached)
   state directory and returns its own path.
2. `_supervisors_for(policy)`: always build a fresh `LiveSupervisors(supervisor_argv)`
   per call (drop the WHOLE_HOST_READ_ONLY singleton shortcut -- LiveSupervisors
   itself does no I/O until `start()` is called, so this costs nothing) using that
   one fresh path. Change its return type to `(SupervisorPort, Path)` so the exact
   same path that went into the compiled argv is the one `Jail` remembers -- compute
   the fresh path exactly once per call, never twice (calling `_supervisor_path()`
   a second time anywhere in the same create_bwrap_jail call would write a second,
   decoy file and leak the real one forever when destroy_jail deletes the wrong
   path -- the one real correctness trap here).
3. `Jail` gains a `supervisor_script: Path | None = None` field (None for a `Jail`
   built directly outside create_bwrap_jail, e.g. tests/e2e/test_processes_gateway.py's
   gateway test -- update that test to pass its own `supervisors=` explicitly now
   that the module-level `_supervisors()` default is gone).
4. `destroy_jail`: once `state is GroupState.GONE` is confirmed (the existing
   check, right before where it would otherwise raise `JailTeardownFailed`),
   delete `jail.supervisor_script` if not None (`Path.unlink(missing_ok=True)` --
   safe against a repeated destroy_jail call on an already-torn-down jail).
5. Delete the now-unused `_supervisor_argv`/`_live_supervisors`/`_supervisors`
   module-level singletons entirely -- `_supervisors_for` is the sole entry point,
   with no special case left to maintain.
6. Tests per the ACs above: single-jail cleanup, two-jails-one-destroyed isolation,
   many-cycles leaves zero files, destroy-without-run still cleans up.

### Proof
- just gates, just typecheck, just done green.
- Real Linux + bwrap (brig-probe-amd64:latest): all new/changed tests pass; the
  existing walking-skeleton and supervisor e2e batteries still pass unmodified.

### Risks
- The "compute the fresh path exactly once, thread it to both the argv and the
  Jail" step is the one place a bug here silently leaks the real file while
  deleting a decoy -- verify by inspection that only one call to
  `_supervisor_path()` happens per `create_bwrap_jail`, not by trusting the
  structure alone.
- Losing the shared LiveSupervisors singleton's one dict tracking many jails'
  open supervisors costs nothing functionally (each jail's own fresh instance
  tracks exactly its own one entry, and `Jail.supervisors` already carries the
  right instance either way) -- confirm this reasoning holds by re-running the
  existing walking-skeleton test, not just asserting it.

Known gap, out of scope for this task's own design: if create_bwrap_jail's run()
raises (e.g. JailSpawnFailed) after _supervisors_for already wrote the script
file, no Jail is ever returned to carry supervisor_script for destroy_jail to
delete later -- that file leaks. Observed independently on this host's own
~/.brig (22 pre-existing orphan files, all predating this session, each 35K,
presumably from other concurrent sessions on this shared host hitting exactly
that path since bwrap isn't installed on macOS). This task's committed design
ties deletion to destroy_jail's GroupState.GONE check, which presupposes a Jail
exists at all -- a create-time failure before a Jail is constructed is a
different, unaddressed failure mode and would need its own design (e.g. deleting
the file in create_bwrap_jail's own exception path) if the owner wants it closed.
