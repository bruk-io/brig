## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

`brig.infra.processes.spawn` (TASK-0001.06's safe-spawn work) calls `os.posix_spawnp(..., setsid=True)` unconditionally. On this host (macOS) that works. Measured while fixing review findings on TASK-0001.05: on real Linux (`ubuntu:24.04`, glibc 2.39, bubblewrap installed), using `uv`'s own managed CPython 3.15 build -- the exact toolchain this project's own `pyproject.toml`/CI configure (`uv run just done`, with `uv` fetching its standalone build the same way `astral-sh/setup-uv` does in `.github/workflows/ci.yml`) -- this line raises:

```
NotImplementedError: posix_spawnp: setsid unavailable on this platform
```

for every single call, with no fallback. Not specific to any one jail type or test: it reproduces for a bare `os.posix_spawnp(..., setsid=True)` call with no bwrap involved at all, and it took down 11 of the 12 tests in `tests/e2e/` in that container -- `test_bwrap_journey.py`, `test_fd_inheritance_battery.py`, `test_processes_gateway.py`, and this task's own `test_tiocsti_battery.py` alike -- not just the ones TASK-0001.05's review touched.

This repository has no `git remote` configured and has never been pushed, so `.github/workflows/ci.yml` has never actually run on GitHub Actions: nothing has caught this yet. As configured today, the first real CI run on `ubuntu-latest` would almost certainly fail `just done` at `test-e2e`, independent of anything TASK-0001.05 changed.

**Root cause, isolated (measured, not a guess):** in the same container, Ubuntu's own packaged `python3` (3.12.3, dynamically linked against the identical glibc 2.39) runs `os.posix_spawnp(..., setsid=True)` successfully. Only `uv`'s managed/standalone CPython 3.15 build raises `NotImplementedError`. So this is not a glibc/platform limitation -- real Linux, this glibc, supports the flag -- it is specifically how `uv`'s portable CPython build for Linux was compiled (its `POSIX_SPAWN_SETSID` support is a compile-time feature check against the headers available when that build was produced, and that build evidently didn't have it, or didn't enable it, regardless of the runtime glibc). The fix is a toolchain-level one: get a `uv`-managed CPython build (a different version, a different build variant, or a report/fix upstream to `python-build-standalone`) that has this compiled in, or stop depending on `setsid=True` being available and fall back to another mechanism on Linux.

## What this task is

Fix this for real on real Linux, under this project's own toolchain (`uv`-managed Python, exactly as `just`/CI invoke it) -- not by hedging between candidate causes; the cause above is isolated. Options to weigh: a different Python version/build where `uv` provides the flag; a runtime capability probe in `brig.infra.processes.spawn` with a documented, equally-safe fallback (e.g. `os.posix_spawnp` without `setsid` followed immediately by... needs its own fork-safety analysis, since TASK-0001.06 moved away from hand-rolled `fork`+`setsid`+`exec` specifically to avoid async-signal-safety hazards); or an upstream report against `python-build-standalone`/`uv` with a pinned workaround until it's fixed there.

Out of scope for this task: anything about TIOCSTI, inherited fds, or bwrap's own flags (TASK-0001.05's own territory) -- this is strictly about whether `spawn()` can run its process at all on real Linux under this project's own toolchain.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## Root cause (confirmed at the compile-time gate, not inferred)

The description's isolation was right that only uv's build is affected, but the mechanism
is narrower than "its `POSIX_SPAWN_SETSID` support is a compile-time feature check":

- `POSIX_SPAWN_SETSID` is **not** an autoconf `HAVE_*`. It is a bare `#define` in glibc's
  `<spawn.h>`, guarded by `#ifdef __USE_GNU`, and it was added in **glibc 2.26**. There is
  no `HAVE_POSIX_SPAWN_SETSID` line in either interpreter's `pyconfig.h` (checked both),
  so `sysconfig`/`posix._have_functions` cannot answer this question at all -- both report
  nothing for it even on the interpreter where the flag works.
- CPython's `posixmodule.c` tests `#ifdef POSIX_SPAWN_SETSID` directly, at compile time,
  and raises `NotImplementedError` from its argument parsing when the macro was absent.
- `_GNU_SOURCE` **is** defined in uv's build (`pyconfig.h:1914`), so the `__USE_GNU` guard
  is not what hides it. The headers simply predate the macro: uv's managed CPython is a
  python-build-standalone build whose max required glibc symbol version is `GLIBC_2.17`
  (`readelf -V libpython3.15.so` -> `GLIBC_2.0`, `GLIBC_2.17` only), i.e. built against a
  glibc 2.17 sysroot for portability. 2.17 < 2.26, so the flag is compiled **out
  permanently**, however new the glibc it later runs against (2.39 here).

Measured consequences:

- **Not a Linux limitation.** Ubuntu's packaged `python3` 3.12.3, on the identical runtime
  glibc 2.39, runs `setsid=True` fine and the child really gets a new sid.
- **Not specific to `posix_spawnp`.** `os.posix_spawn` (absolute path) raises identically;
  the gate is in shared flag parsing, not the PATH-searching variant.
- **Not fixable by pinning a version or variant.** Every uv-managed build raises: 3.12.15,
  3.13.16, 3.14.8, 3.15.0, and 3.14t (freethreaded), on both aarch64 and x86_64. So
  "pick a Python where the flag works" is not available -- and it would be the wrong fix
  regardless: brig is a standalone library and cannot dictate its embedder's interpreter
  build.
- `setpgroup=0` works everywhere, and gives the child a new process group whose pgid is
  its own pid (verified: `pgid == pid` under the real `spawn`, with file_actions, on both
  arches).

## Fix

`src/brig/infra/processes.py`: new `_spawn_leading_a_new_group` asks for `setsid=True`,
catches `NotImplementedError` **around that one call only**, and retries with
`setpgroup=0`. `NotImplementedError` is raised during argument parsing before any fork,
so nothing is started and the retry is safe. `OSError -> SpawnError` handling is unchanged
and covers both paths. Fork safety is fully preserved: both are flags `posix_spawnp` acts
on inside libc, so neither runs Python after a fork -- TASK-0001.06's reason for leaving
`os.fork()` behind is untouched.

`SpawnedProcess` gains **`session_detached: bool`**. This is the part that matters for a
library whose job is grading: the fallback is a genuinely weaker boundary, and rather than
let it hold silently on one interpreter and not another, infra now reports which guarantee
it actually got. `pgid == pid` holds on both paths, so teardown (`signal_group`,
`group_alive`) is unaffected and the domain/port types did not need to change.

### Alternatives rejected

- **Unconditional `setpgroup=0`** (uniform behaviour, tidier docstrings): would delete a
  security property that works and is verified on macOS, to make the two platforms agree
  on the weaker answer. Divergence is better handled by reporting it than by levelling down.
- **A different uv Python**: measured unavailable (all versions/variants/arches above), and
  wrong in principle for a library.
- **`sys.platform` / `sysconfig` probe**: cannot work -- the property is per-build, and
  `pyconfig.h` records nothing for it on either interpreter.

### Honest gap

Where `session_detached` is `False`, the spawned process keeps the caller's controlling
terminal, so the TIOCSTI hole is **not** closed by infra. For the bwrap jail type it is
closed by bwrap's own `--new-session` -- verified for real (below). For a future jail type
whose argv does not detach a session, infra no longer closes it; that is now visible in the
return value instead of assumed.

### Attribution inverts (and three docstrings with it)

TASK-0001.05's review recorded, as measured fact, that infra's unconditional `setsid`
always ran first and therefore `--new-session` could never be credited. That is false on
this project's own CI toolchain: there `session_detached` is `False` and `--new-session` is
the **only** thing closing TIOCSTI -- so AC#2's attribution is gradable there after all.
Updated accordingly: `domain/jail_types/bwrap.py`'s `_BWRAP_ARGV` docstring,
`tests/e2e/test_tiocsti_battery.py`'s module docstring, and
`src/brig/presentation/ports.py` (`_ProcessIdentity` prose + `spawn`'s "session and group"
claim). TASK-0001.11 still owns grading the attribution directly.

`test_tiocsti_injection_fails_once_infra_detaches_the_session` graded a claim infra does
not always make, so it now skips -- with the measurement as its reason, via
`_skip_if_infra_cannot_detach_a_session`, which asks `spawn` itself -- where the flag is
absent, matching the existing `CONFIG_LEGACY_TIOCSTI=n` skip pattern and the
`python-tests-e2e` rule ("reported as not run, never counted as a pass"). The real-jail
battery still asserts the hole is closed, which is the right assertion either way.

## Attribution, measured with a negative control (answers TASK-0001.05 AC#2, and unblocks TASK-0001.11)

Run on Linux x86_64 under uv's CPython 3.15, i.e. with `session_detached = False`, driving brig's real `spawn` inside a `pty.fork()` session:

| case | result |
| --- | --- |
| positive control, no jail, owns the pty | **INJECTED -- hole open** |
| brig's real bwrap argv (with `--new-session`) | **denied, EPERM** |
| same argv, `--new-session` removed | **INJECTED -- hole open** |

The third row is the negative control that was missing. It establishes, rather than infers, that `--new-session` is the **sole** closer of the TIOCSTI hole on this toolchain: `--unshare-all` and `--die-with-parent` are present in all three bwrap rows and do not close it, and infra detaches no session here. So AC#2's claim -- that bwrap's `--new-session` closes this hole "and not infra's setsid" -- **holds for real on this project's own CI platform**, not merely in principle.

Consequence for TASK-0001.11, whose premise was that no black-box battery can attribute the closure: that premise is now false wherever `session_detached` is `False`. A differential battery is buildable there -- run the probe through a bwrap argv with and without `--new-session` and require the first to be denied and the second to inject. Deliberately **not** added here: it needs an argv that `domain/jail_types/bwrap.py`'s `compile_run` does not produce, so where that negative-control argv may legitimately come from is a test-design decision belonging to TASK-0001.11, not to this fix. Script used for the measurement is not checked in.

On macOS, where `session_detached` is `True`, the attribution remains ungradable exactly as TASK-0001.05's review described: infra's session detaches first and already suffices.
