## Why

`brig.infra.processes.spawn` (TASK-0001.06's safe-spawn work) calls `os.posix_spawnp(..., setsid=True)` unconditionally. On this host (macOS) that works. Measured while fixing review findings on TASK-0001.05: on real Linux (`ubuntu:24.04`, glibc 2.39, bubblewrap installed), using the exact toolchain this project's own `pyproject.toml`/CI configure (`uv run just done`, with `uv` fetching its own standalone CPython 3.15 build the same way `astral-sh/setup-uv` does in `.github/workflows/ci.yml`), this line raises:

```
NotImplementedError: posix_spawnp: setsid unavailable on this platform
```

for every single call, with no fallback. This is not specific to any one jail type or test: it reproduces for a bare `os.posix_spawnp(..., setsid=True)` call with no bwrap involved at all, and it took down 11 of the 12 tests in `tests/e2e/` in that container -- `test_bwrap_journey.py`, `test_fd_inheritance_battery.py`, `test_processes_gateway.py`, and this task's own `test_tiocsti_battery.py` alike -- not just the ones this task's review touched.

This repository has no `git remote` configured and has never been pushed, so `.github/workflows/ci.yml` has never actually run on GitHub Actions: nothing has caught this yet. As configured today, the first real CI run on `ubuntu-latest` would almost certainly fail `just done` at `test-e2e`, independent of anything TASK-0001.05 changed.

Likely cause (not confirmed further): CPython's `os.posix_spawn` support for the `POSIX_SPAWN_SETSID` flag is a compile-time feature check against the libc headers present when that specific CPython build was compiled, not a runtime check against the glibc actually running it. The portable/standalone CPython builds `uv python install` downloads for Linux may have been compiled without that flag available, regardless of the runtime glibc version (2.39 here) actually supporting it. This would mean every Linux host using `uv`'s managed Python hits this, not just this one container.

## What this task is

Investigate and fix (or work around) the real root cause so `brig.infra.processes.spawn`'s `setsid=True` path works on real Linux under this project's own toolchain -- for example: confirm against a non-uv-managed system Python on real Linux whether the flag works there (isolating "uv's build" vs "glibc 2.39" as the cause), and either get a CPython build where it's compiled in, or fall back to the hand-rolled `os.fork()` + `os.setsid()` + `os.execvpe()` design TASK-0001.06 explicitly moved away from (reintroducing the fork-safety tradeoff that move was for), or another mechanism that keeps both the safety property and real Linux support.

Out of scope for this task: anything about TIOCSTI, inherited fds, or bwrap's own flags (TASK-0001.05's own territory) -- this is strictly about whether `spawn()` can run its process at all on real Linux.
