## Why

`brig.infra.processes.spawn` (TASK-0001.06's safe-spawn work) calls `os.posix_spawnp(..., setsid=True)` unconditionally. On this host (macOS) that works. Measured while fixing review findings on TASK-0001.05: on real Linux (`ubuntu:24.04`, glibc 2.39, bubblewrap installed), using `uv`'s own managed CPython 3.15 build -- the exact toolchain this project's own `pyproject.toml`/CI configure (`uv run just done`, with `uv` fetching its standalone build the same way `astral-sh/setup-uv` does in `.github/workflows/ci.yml`) -- this line raises:

```
NotImplementedError: posix_spawnp: setsid unavailable on this platform
```

for every single call, with no fallback. Not specific to any one jail type or test: it reproduces for a bare `os.posix_spawnp(..., setsid=True)` call with no bwrap involved at all, and it took down 11 of the 12 tests in `tests/e2e/` in that container -- `test_bwrap_journey.py`, `test_fd_inheritance_battery.py`, `test_processes_gateway.py`, and this task's own `test_tiocsti_battery.py` alike -- not just the ones TASK-0001.05's review touched.

This repository has no `git remote` configured and has never been pushed, so `.github/workflows/ci.yml` has never actually run on GitHub Actions: nothing has caught this yet. As configured today, the first real CI run on `ubuntu-latest` would almost certainly fail `just done` at `test-e2e`, independent of anything TASK-0001.05 changed.

**Root cause, isolated (measured, not a guess):** in the same container, Ubuntu's own packaged `python3` (3.12.3, dynamically linked against the identical glibc 2.39) runs `os.posix_spawnp(..., setsid=True)` successfully. Only `uv`'s managed/standalone CPython 3.15 build raises `NotImplementedError`. So this is not a glibc/platform limitation -- real Linux, this glibc, supports the flag -- it is specifically how `uv`'s portable CPython build for Linux was compiled (its `POSIX_SPAWN_SETSID` support is a compile-time feature check against the headers available when that build was produced, and that build evidently didn't have it, or didn't enable it, regardless of the runtime glibc). The fix is a toolchain-level one: get a `uv`-managed CPython build (a different version, a different build variant, or a report/fix upstream to `python-build-standalone`) that has this compiled in, or stop depending on `setsid=True` being available and fall back to another mechanism on Linux.

## What this task is

Fix this for real on real Linux, under this project's own toolchain (`uv`-managed Python, exactly as `just`/CI invoke it) -- not by hedging between candidate causes; the cause above is isolated. Options to weigh: a different Python version/build where `uv` provides the flag; a runtime capability probe in `brig.infra.processes.spawn` with a documented, equally-safe fallback (e.g. `os.posix_spawnp` without `setsid` followed immediately by... needs its own fork-safety analysis, since TASK-0001.06 moved away from hand-rolled `fork`+`setsid`+`exec` specifically to avoid async-signal-safety hazards); or an upstream report against `python-build-standalone`/`uv` with a pinned workaround until it's fixed there.

Out of scope for this task: anything about TIOCSTI, inherited fds, or bwrap's own flags (TASK-0001.05's own territory) -- this is strictly about whether `spawn()` can run its process at all on real Linux under this project's own toolchain.
