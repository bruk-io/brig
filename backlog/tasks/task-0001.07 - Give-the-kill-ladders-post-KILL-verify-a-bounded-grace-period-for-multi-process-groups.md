## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

TASK-0001.06's review found that infra.reap() could leak a raw ChildProcessError
when a jail's leader exits (and is reaped by an earlier Verify's reap_nowait) before
the rest of its group does -- the leader's post-KILL Reap then hits ECHILD. That
finding's own fix (reap() returns ProcessUnknown instead of raising; teardown
discards it) is in, verified, and closes TASK-0001.06's three acceptance criteria.

Fixing it surfaced a second, narrower problem in the same code path, confirmed by
running the review's own reproduction in a tight loop against the fixed code
(no bwrap required):

```python
from brig.domain.effects import Process
from brig.presentation.api import Jail, destroy_jail
from brig.infra.processes import spawn
import time

sp = spawn(("/bin/sh", "-c", "trap '' TERM; sleep 30 & exit 0"))
time.sleep(0.03)  # let the leader exit and get collected by the first Verify
destroy_jail(Jail(process=Process(pid=sp.pid, pgid=sp.pgid)))
```

This now raises `JailTeardownFailed` (a proper brig error -- no raw exception
escapes, TASK-0001.06's own bar is met) essentially every time on this machine, even
though the group genuinely does die from SIGKILL a short moment later (confirmed by
re-checking `group_alive` after a 0.1s pause: it reports gone).

## Root cause

`domain/teardown.py`'s kill ladder relies on the post-KILL `Reap` of the leader to
act as a synchronization barrier: by blocking until the leader exits, it guarantees
the kernel has finished processing SIGKILL before the final `Verify` runs right
after (the module's own docstring: "collecting it here first means the Verify that
follows always sees it gone"). That barrier assumed a single-process jail, where the
leader IS the whole group.

Once the leader can already be gone (ECHILD) by the time this Reap runs -- exactly
the multi-process-group case TASK-0001.06's review introduced ProcessUnknown for --
that Reap returns instantly instead of blocking, so the final Verify can run before
SIGKILL has actually finished taking effect on the rest of the group. The ladder
still reports a real, well-typed brig error (JailTeardownFailed), never a crash or a
hang, but it is a false negative: the group was not actually un-killable, the check
just ran too soon.

A real bwrap jail is a multi-process group (bwrap plus its namespaced child), which
is why TASK-0001.06's review flagged this as the path its AC3 e2e test exercises in
Linux CI -- though note that under bwrap's normal supervising behaviour (it waits for
its child rather than exiting early), the leader-already-gone precondition for this
race may not actually arise; that needs checking for real on Linux, where bwrap is
available, since this repo's dev machine is macOS and cannot run bwrap at all.

## What this task should do

1. On a Linux host with bwrap, confirm whether `destroy_jail` against a real bwrap
   jail ever hits the leader-already-reaped precondition in practice (does bwrap's
   own process ever exit before its sandboxed child's group fully dies?).
2. If it can, design a bounded way for the kill ladder's post-KILL step to give the
   rest of a multi-process group a short, finite grace window before the final
   Verify decides -- not an open-ended wait (that would reintroduce the hazard
   TASK-0001.06 closed), and not the "grace period between TERM and KILL" that
   decision-0001's teardown.py docstring already defers to a later slice: this is
   specifically about the gap between KILL and the verify right after it, for a
   group whose leader can no longer provide that wait by blocking. It likely needs
   a new primitive (something like a deadline-bound group-aliveness poll,
   analogous to reap_deadline but for a pgid) and a matching domain effect.
3. Decide whether this needs its own decision record, given decision-0001 already
   treats "the general ladder" as a design question for a later slice.

## Evidence

Confirmed on this machine (macOS, no bwrap): 200/200 runs of the reproduction above
raised JailTeardownFailed; manually re-checking group_alive 0.1s later each time
showed the group was in fact gone. Not a rare flake -- on this machine, with no
deliberate delay between KILL and the final Verify, it reproduces close to 100% of
the time for this leader-exits-early shape.
